# 架构决策记录

## ADR-001：与 VideoNote-MCP 完全解耦

状态：已决定。

Agent-VideoNote 不复制、不 import、不运行依赖 VideoNote-MCP。

原因：

- 当前实际只使用旧项目少量底层能力。
- 旧项目大量功能增加维护、上下文和依赖负担。
- 用户希望未来具备商用可能，不希望再次做二次脱钩。

## ADR-002：模块化优先

状态：已决定。

媒体、ASR、任务、视觉、工作流、交付、协议适配分开。

不建立新的“大型 server.py / utils.py / manager.py”承载全部逻辑。

## ADR-003：协议层必须薄

状态：已决定。

MCP 只是入口，未来如果增加 CLI 或其他 Agent 协议，不应复制核心业务逻辑。

## ADR-004：运行数据与源码分离

状态：已决定。

任务帧、切片、模型、备份、未解决案例不得堆在源码仓库中。

## ADR-005：普通任务不造正式脚本

状态：已决定。

PROCESS 遇到已有工具无法处理的问题时记录 unresolved；需要新能力时进入 MAINTENANCE，正式实现并增加测试。

## ADR-006：生成式图像修复不作为默认能力

状态：已决定。

GPT 图像 AI / 付费生成式修图不进入默认工作流。

## ADR-007：第三方来源直接对接上游

状态：已决定。

FFmpeg、ASR 框架/模型、PyTorch、MCP SDK 等若采用，直接针对其官方/上游项目集成并单独审核许可证，不通过 VideoNote-MCP 间接继承。

## ADR-008：ASR 角色固定，具体实现可替换

状态：已决定。

系统层只定义 `primary`、`review`、`context` 等能力角色，不把具体模型名写入工作流、任务状态或 MCP 协议。

具体实现通过 Provider 注册并声明能力，由 profile 配置角色映射。

历史使用过的 Fun-ASR-Nano-2512、Qwen3-ASR-1.7B 只作为候选 Provider 的实战参考，不构成架构依赖。

目标：

- 换模型不改工作流；
- 换模型不改任务协议；
- 换模型不改 MCP 工具名称；
- 同一 Provider 可以承担多个角色；
- 某角色可以关闭；
- Provider 不支持某能力时显式失败，不偷偷降级。

## ADR-009：成熟能力优先复用，不重复造算法轮子

状态：已决定。

新增或扩展能力前，先检查成熟上游项目/库；能通过 Provider / Adapter 安全复用时，优先复用。

Agent-VideoNote 自己维护的重点是：

- task / artifact 状态；
- 断点恢复与幂等；
- Provider Registry；
- MCP 薄层；
- 安全门槛与回滚；
- clean / resolved / unresolved 等工作流语义；
- 课程上下文与最终交付编排。

成熟第三方更适合承担的算法能力，例如 ASR、OCR、视频补全、场景检测、字符串相似度，不在本项目重新实现一套模型或通用算法。

限制：

- 第三方大仓库优先作为外部 Provider 调用，不整仓复制；
- 许可证、模型权重和代码许可证分别审核；
- 已经真实验证稳定的自研模块不为了“换库”而无收益重写；
- OCR/文字检测结果不能直接变成删除 mask，必须经过上层安全判断。
